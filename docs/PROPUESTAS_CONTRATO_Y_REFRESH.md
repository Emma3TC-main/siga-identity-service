## Refresh web: evidencia y responsabilidad

**Definido:** Manual §3.2 asigna refresh/MFA/revocación a Identity; §7.1 exige rotación, access 30 minutos y refresh 7 días; §7.6 exige access en memoria y refresh HttpOnly/Secure/SameSite, CORS explícito y evaluación de CSRF. §7.7 distingue Mobile/SecureStore. ADR-012 asigna routing/CORS/rate-limit/correlation a Gateway, sin negocio. `diagramas/secuencia/SEQ_15_Frontend_Refresh.puml` muestra cookie enviada al Gateway, reenvío a IAM y respuesta IAM→Web con refresh rotado en cookie. `SEQ_02_Refresh_Token.puml` admite cookie/SecureStore.

**No definido de forma suficiente:** nombre/path/dominio/SameSite concreto, emisor técnico de Set-Cookie, adaptación Web/Mobile, obtención y validación de CSRF, limpieza de cookie en logout y comportamiento de errores. OpenAPI exige refreshToken JSON de entrada y salida; no contiene cookies ni CSRF. Por eso no hay un contrato web cookie ejecutable aprobado. No hay un BFF aprobado en estas fuentes.

**Propuesta preferida:** Identity emite, rota y elimina la cookie en el transporte web; Gateway reenvía Cookie/Set-Cookie y aplica CORS/orígenes/TLS según el entorno. Es la opción más cercana al ownership IAM y SEQ-15; la atribución técnica detallada sigue pendiente de aprobación. No implementar lógica de sesión en Gateway ni un BFF nuevo.

| Alternativa | Efecto y coste | Estado |
|---|---|---|
| Identity gestiona cookie y CSRF web; Gateway conserva transporte | Mantiene sesión y validación CSRF juntas; requiere ampliar contrato Identity para distinguir Web/Mobile | Recomendada, pendiente |
| Gateway convierte cookie a JSON y JSON a Set-Cookie | Puede mantener el transporte interno actual, pero requiere política de sesión/CSRF y adaptación de respuestas en Gateway, ausentes de ADR-012 | Requiere revisar frontera del Gateway; no asumida |
| BFF dedicado | Nuevo componente, contrato y operación, sin respaldo en la arquitectura actual | No propuesto para implementar; necesita ADR si se elige |

Detalle candidato para revisar: cookie host-only `__Secure-siga_refresh`, HttpOnly, Secure, Path `/api/v1/auth`, SameSite=Lax para despliegue web del mismo sitio, Max-Age acorde a los siete días; rotarla en login/MFA/refresh y eliminarla con los mismos atributos en logout. Si Web y API son sitios distintos, revisar SameSite=None+Secure, CORS con credenciales y riesgos; no adoptarlo automáticamente. El ensayo HTTP local de esta tarea no implementa cookies ni sustituye una validación HTTPS de navegador.

**CSRF propuesto:** Identity valida un token CSRF ligado a la sesión/contexto de autenticación en todas las operaciones que usen credenciales enviadas automáticamente por el navegador, incluidos login, verificación MFA, refresh y logout web. Definir emisión previa a login y renovación posterior; rechazar ausencia/valor incorrecto y origen no permitido. Gateway aplica allowlist de Origin/CORS y no elimina la cabecera CSRF. SameSite no se toma como protección única. Debe decidirse el mecanismo (token sincronizado o double-submit firmado), bootstrap del token y su contrato antes de implementar; no hay endpoint `/auth/csrf` aprobado hoy.

**Impacto contractual:** documentar Cookie/Set-Cookie, CSRF y errores; respuesta web sin refreshToken en JSON para que permanezca HttpOnly; preservar transporte JSON explícito para Mobile/SecureStore; rechazar ambigüedad si llegan ambas credenciales. Decidir si se versiona o separa el transporte web para no romper los clientes actuales. Los tests actuales validan JSON y no demuestran cookies/CSRF. La desactivación CSRF actual solo cubre ese modo JSON sin cookie de autenticación.

## Política local de operación aplicada

Manual §15 prevé Actuator/Micrometer→Prometheus y liveness/readiness, pero no define autenticación operativa por entorno. Se implementa **solo en perfil local** un listener de management separado en 127.0.0.1, acceso GET desde loopback a health/probes/prometheus, sin detalles/componentes de health ni otros actuators. El puerto de API no autoriza métricas. Liveness depende del estado interno; readiness añade PostgreSQL y Redis usados para autenticación. RabbitMQ no bloquea readiness porque outbox conserva eventos, aunque la salud agregada informa su caída.

Consumidores locales admitidos: PowerShell y Prometheus ejecutado en el mismo host Windows. Un Prometheus en contenedor no accede a ese binding: su ruta/autenticación requerirá una configuración distinta revisada. No se abre management a LAN ni se publica un acceso público. DEV/QA/PROD y el despliegue de observabilidad quedan pendientes de política explícita (red privada, identidad del scraper/autenticación y TLS), sin trasladar automáticamente la excepción local.
